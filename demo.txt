==============================================================================
 HOW TO DEMO THIS PROGRAM
 Secure Communication Between Alice and Bob Using AES-256-GCM
 Two terminals: alice.py (sender) and bob.py (receiver)
==============================================================================

This file is a step-by-step demo script. Follow the numbered steps in two
terminal windows and you will reproduce the output shown below.

Every Base64 value (nonce, ciphertext, tag) and every key fingerprint is
RANDOM on each run, so yours will look different. The wording of the messages
will be identical.

The exact same session is saved in sample_output.txt.


------------------------------------------------------------------------------
 PART 1 - ONE-TIME SETUP (do this before the demo)
------------------------------------------------------------------------------

STEP 0. Open TWO terminals in the project folder.

    Windows PowerShell (do this in both windows):

        cd "C:\Users\GAURAV\OneDrive\Desktop\Sem5\Cryptography\pbl"

    macOS / Linux (do this in both windows):

        cd path/to/pbl

    Name them in your head:

        LEFT  window  = Terminal 1 = Alice = the sender
        RIGHT window  = Terminal 2 = Bob   = the receiver


STEP 1. Check Python is available (3.10 or newer is required).

        python --version

    Example output:

        Python 3.14.6

    On macOS/Linux you may need "python3" instead of "python" everywhere in
    this document.


STEP 2. Install the dependency.

        pip install -r requirements.txt

    If you already have a virtual environment, activate it first:

        Windows:      .\.venv\Scripts\Activate.ps1
        macOS/Linux:  source .venv/bin/activate


STEP 3. (Recommended) Start from a clean slate so Stage 1 really generates a
        new key. In EITHER terminal, if these files exist, delete them:

        Windows PowerShell:

            Remove-Item -ErrorAction SilentlyContinue secret.key, encrypted_message.json

        macOS / Linux:

            rm -f secret.key encrypted_message.json

    Do NOT delete anything else. The scripts and docs are untouched.


------------------------------------------------------------------------------
 PART 2 - THE DEMO ITSELF
------------------------------------------------------------------------------

STEP 4. In TERMINAL 1 (Alice), run:

        python alice.py

    Alice prints a banner, then STAGE 1: KEY GENERATION.

    Expected output (fingerprint and key will differ):

        ==============================================================
          Secure Communication - AES-256-GCM
          TERMINAL 1 - ALICE (sender)
        ==============================================================
          Alice encrypts a private message and writes the package
          file that Bob will open with bob.py in a second terminal.
          Shared key file: secret.key
          Package file  : encrypted_message.json

        ==============================================================
          STAGE 1: KEY GENERATION
        ==============================================================
          No secret.key yet, creating one now.
          [OK] Generating a 256-bit key with os.urandom(32) (CSPRNG).
          Key length                  : 256 bits
          Key fingerprint             : 245d12d462970acc
          Saved to                    : secret.key
          Give secret.key to Bob through a secure channel - in person, a
          password manager, or similar. Never send it with the ciphertext.

    TALKING POINT - the key:
      - The key is 32 random bytes = 256 bits, straight from the operating
        system's secure random generator (os.urandom). Never from "random".
      - The fingerprint is the first 16 hex characters of SHA-256(key). It is
        safe to read aloud: you cannot turn it back into the key. It just lets
        Alice and Bob confirm they hold the same key.
      - secret.key now exists in the project folder. This is the shared secret.

    NOTE - if secret.key already existed, Alice would instead show the
    fingerprint and ask:

          Generate a new key instead? Bob needs the same key. [y/N]:

      Press Enter (or type "n") to keep the existing key. That is the safe
      choice: if you replace it, Bob must receive the new secret.key or his
      decryption will fail. Answer "y" only if you intend to re-share the key.


STEP 5. At the prompt

        Plaintext message:

    type a message and press Enter. Use this one for the demo:

        Meet me at the library at 5 PM.

    Alice encrypts it and prints STAGE 2: ENCRYPTION — ALICE.

    Expected output:

        ==============================================================
          STAGE 2: ENCRYPTION — ALICE
        ==============================================================
          Type the message Alice wants to send to Bob.
          It is encrypted before anything is written to disk.

          Plaintext message: Meet me at the library at 5 PM.

          Encryption result:
          Algorithm                   : AES-256-GCM
          Original plaintext          : Meet me at the library at 5 PM.
          Nonce (96-bit, Base64)      :
              869johMRYgTBa00r
          Ciphertext (Base64)         :
              uIsIylJ/sIL3hTNxxjy9Ju1/nzPSWUZQlZbV4lngAmXInfuRbwyG/y1VIBQOG14=
          Authentication tag (Base64) :
              Zcid+5FvDIb/LVUgFA4bXg==
          Ciphertext length           : 31 bytes + 16-byte tag

          Every encryption uses a fresh 96-bit nonce, so the same message
          encrypted twice never produces the same output.

    TALKING POINT - the three values:

      1. NONCE (96 bits / 12 bytes)
         A number used once. It is random, it is NOT secret, and it is sent
         with the message. Encrypting the same message twice gives a
         completely different nonce and ciphertext. Reusing a nonce with the
         same key would break GCM badly, so the code creates a new one inside
         encrypt_message() on every call.

      2. CIPHERTEXT (31 bytes here)
         The encrypted message. In the "cryptography" library this value
         already has the 16-byte authentication tag stuck on the end:
                ciphertext_on_disk = real_ciphertext || tag
         That is why the ciphertext is 31 + 16 = 47 bytes long (63 Base64
         characters ending in "=").

      3. AUTHENTICATION TAG (128 bits / 16 bytes)
         A value computed from the key, the nonce and the ciphertext. Bob
         recomputes it when he decrypts. If one bit anywhere is different,
         the tag will not match and decryption fails.

    The message is encrypted in memory BEFORE anything is written to disk.


STEP 6. Alice now runs STAGE 3: MESSAGE TRANSFER and writes the package.

    Expected output:

        ==============================================================
          STAGE 3: MESSAGE TRANSFER
        ==============================================================
          Alice writes the encrypted package for Bob:
          Package file                : encrypted_message.json
          Sender                      : Alice
          Recipient                   : Bob
          Contents                    : nonce + ciphertext + authentication tag
          Secret key inside package   : no - it stays in secret.key
          Key fingerprint (for Bob)   : 245d12d462970acc

        Message encrypted and ready for Bob.
        Next: open Terminal 2 and run   python bob.py

    TALKING POINT - what crossed the "insecure channel":
      - encrypted_message.json contains the nonce, the ciphertext (with the
        tag appended), display metadata and the key fingerprint.
      - It contains NO secret key. Anyone can read the file; without secret.key
        they cannot recover the message or forge a valid tag.
      - A real attacker who reads this file sees only random-looking Base64.

    OPTIONAL - show the file on screen:

        Windows PowerShell:   Get-Content encrypted_message.json
        macOS / Linux:        cat encrypted_message.json

    You will see JSON like this:

        {
          "algorithm": "AES-256-GCM",
          "package_version": 1,
          "created_at": "2026-11-22T09:34:54+00:00",
          "sender": "Alice",
          "recipient": "Bob",
          "nonce": "869johMRYgTBa00r",
          "ciphertext": "uIsIylJ/sIL3hTNxxjy9Ju1/nzPSWUZQlZbV4lngAmXInfuRbwyG/y1VIBQOG14=",
          "authentication_tag": "Zcid+5FvDIb/LVUgFA4bXg==",
          "plaintext_bytes": 31,
          "key_fingerprint": "245d12d462970acc"
        }


STEP 7. In TERMINAL 2 (Bob), run:

        python bob.py

    Bob prints a banner, then STAGE 3: MESSAGE TRANSFER. There is nothing to
    type: Bob just loads secret.key and encrypted_message.json.

    Expected output:

        ==============================================================
          Secure Communication - AES-256-GCM
          TERMINAL 2 - BOB (receiver)
        ==============================================================
          Bob reads the shared key and the package that Alice wrote.
          Run alice.py in Terminal 1 first.
          Shared key file: secret.key
          Package file  : encrypted_message.json

        ==============================================================
          STAGE 3: MESSAGE TRANSFER
        ==============================================================
          Bob looks for the shared key and the encrypted package ...

          Shared key file             : secret.key
          Key fingerprint (local)     : 245d12d462970acc

          Package received:
          Package file                : encrypted_message.json
          Sender                      : Alice
          Created at                  : 2026-11-22T09:34:54+00:00
          Plaintext size              : 31 bytes
          Nonce (96-bit, Base64)      :
              869johMRYgTBa00r
          Ciphertext (Base64)         :
              uIsIylJ/sIL3hTNxxjy9Ju1/nzPSWUZQlZbV4lngAmXInfuRbwyG/y1VIBQOG14=
          Authentication tag (Base64) :
              Zcid+5FvDIb/LVUgFA4bXg==
          Ciphertext length           : 31 bytes + 16-byte tag

    TALKING POINT - validation:
      Before using anything, Bob validates the package: valid JSON, correct
      algorithm, valid Base64, a 12-byte nonce, a ciphertext of at least 16
      bytes, and a display tag that matches the tag appended to the
      ciphertext. A corrupt package produces a clear [FAIL] and exit code 1,
      not a crash and not a bogus decryption.


STEP 8. Bob moves to STAGE 4: DECRYPTION — BOB.

    Expected output:

        ==============================================================
          STAGE 4: DECRYPTION — BOB
        ==============================================================
          Algorithm                   : AES-256-GCM
          Key fingerprint (package)   : 245d12d462970acc
          Key fingerprint (local)     : 245d12d462970acc

          Verifying the authentication tag and decrypting ...
          [PASS] Authentication tag verified with the shared key.
          [PASS] Decryption succeeded.
          Recovered plaintext         : Meet me at the library at 5 PM.

    TALKING POINT - authenticate, then decrypt:
      AES-GCM does NOT hand Bob unverified data. It checks the tag first. Only
      if the tag matches does it release the plaintext. If the tag fails, the
      library raises InvalidTag and Bob gets NOTHING - not even a partial or
      corrupted message.

    TALKING POINT - the fingerprint comparison:
      The package says the key fingerprint should be 245d12d462970acc. Bob
      computes the fingerprint of his local secret.key and compares. If they
      differ, Bob prints:

          [WARN] The package was encrypted with a different key.
                 The authentication check below will fail.

      before trying, so the cause is obvious.


STEP 9. Bob finishes with STAGE 5: SECURITY VERIFICATION. He runs the three
    checks on the message he just received, so no extra setup is needed.

    Expected output:

        ==============================================================
          STAGE 5: SECURITY VERIFICATION
        ==============================================================
          Test 1 - correct key must decrypt the message
          [PASS] Decryption succeeded and the plaintext matches.

          Test 2 - incorrect key must be rejected
          Alice's key                 : fingerprint 245d12d462970acc
          Bob's wrong key             : fingerprint 5b2f0e71c9c4a8dd
          [PASS] Rejected with InvalidTag; no plaintext was revealed.

          Test 3 - modified ciphertext must be rejected
          Original ciphertext (Base64):
              uIsIylJ/sIL3hTNxxjy9Ju1/nzPSWUZQlZbV4lngAmXInfuRbwyG/y1VIBQOG14=
          Tampered ciphertext (Base64):
              uYsIylJ/sIL3hTNxxjy9Ju1/nzPSWUZQlZbV4lngAmXInfuRbwyG/y1VIBQOG14=
          [PASS] Rejected with InvalidTag; the tampering was detected.

          Result: 3 of 3 security checks passed.

    TALKING POINT - what the three checks prove:

      CHECK 1 - correct key works.
        Same key on both sides: the tag verifies and the plaintext matches
        Alice's original.

      CHECK 2 - wrong key is rejected.
        Bob makes a brand-new random 256-bit key and tries to decrypt. The tag
        is derived from the key, so it does not match. InvalidTag is raised and
        no plaintext leaks. The two fingerprints printed prove the keys really
        are different, without revealing either key.

      CHECK 3 - modified ciphertext is rejected.
        Bob flips ONE bit of the ciphertext (the first character changes from
        "u" to "y" in the Base64 shown). The nonce and key are unchanged, yet
        the tag check fails. This is the whole point of an authenticated
        cipher: ANY change is detected.

    The final line is the result: "3 of 3 security checks passed."

    If you only need the result line without scrolling, on Windows PowerShell:

        python bob.py | Select-Object -Last 1

    On macOS/Linux:

        python bob.py | tail -n 1

 PART 3 - OPTIONAL VARIATIONS (great for questions)
------------------------------------------------------------------------------

VARIATION A - Send a different message.

    Run in Terminal 1:      python alice.py

    If asked whether to generate a new key, press Enter to KEEP the existing
    key. Then type a new message. Run "python bob.py" again in Terminal 2.

    What to say:
      - The ciphertext and tag are completely different even if you send the
        SAME message again, because every encryption gets a fresh random nonce.
      - The key did not change, so Bob still decrypts successfully.

    Quick proof of "fresh nonce" (Windows PowerShell, Terminal 1):

        $n1 = (python -c "import json;print(json.load(open('encrypted_message.json'))['nonce'])")
        "n`nSame message again.`n" | python alice.py
        $n2 = (python -c "import json;print(json.load(open('encrypted_message.json'))['nonce'])")
        "nonce before = $n1"
        "nonce after  = $n2"

    The two nonces are different. (The "n"+"Enter" pair answers the key prompt
    with "keep", so the next line is the message.)


VARIATION B - Bob uses the WRONG key.

    Generate a throwaway key, let Bob fail, then restore Alice's key.

    Windows PowerShell:

        Copy-Item secret.key secret.key.backup
        python -c "from crypto_utils import generate_key, save_key; save_key(generate_key())"
        python bob.py
        Copy-Item secret.key.backup secret.key
        Remove-Item secret.key.backup

    Expected result (last lines):

          [WARN] The package was encrypted with a different key.
                 The authentication check below will fail.
          ...
          [FAIL] Authentication failed.
          The key is wrong, or the nonce/ciphertext/tag was modified
          in transit. No plaintext is released when the tag fails.

          Ask Alice to check that you both use the same secret.key.

    Exit code is 2. Bob stops after the failure and does NOT run Stage 5.
    What to say: a wrong key is caught by the tag, not by "reading garbage".


VARIATION C - Tamper with the ciphertext in the file.

    Windows PowerShell, in Terminal 1:

        Copy-Item encrypted_message.json encrypted_message.json.backup
        python -c "import json,base64; p=json.load(open('encrypted_message.json')); c=bytearray(base64.b64decode(p['ciphertext'])); c[0]^=1; p['ciphertext']=base64.b64encode(bytes(c)).decode(); p['authentication_tag']=base64.b64encode(bytes(c[-16:])).decode(); json.dump(p,open('encrypted_message.json','w'))"
        python bob.py
        Copy-Item encrypted_message.json.backup encrypted_message.json
        Remove-Item encrypted_message.json.backup

    The tag check fails and no plaintext is released (exit code 2).

    Note: the script also rewrites authentication_tag so Bob's metadata check
    passes; this proves the REAL protection is the tag verification during
    decryption, not just a JSON sanity check.


VARIATION D - Missing files.

    Bob with no secret.key:

        Windows:  Move-Item secret.key secret.key.off
                  python bob.py
                  Move-Item secret.key.off secret.key

        Result:   [FAIL] secret.key not found in this folder.        (exit 1)

    Bob with no package:

        Windows:  Move-Item encrypted_message.json encrypted_message.json.off
                  python bob.py
                  Move-Item encrypted_message.json.off encrypted_message.json

        Result:   [FAIL] encrypted_message.json not found in this folder.  (exit 1)

    What to say: the scripts fail with a specific, friendly message and a
    distinct exit code, never with a Python traceback.


VARIATION E - Empty message.

    In Terminal 1 run "python alice.py", keep the key, then press Enter with no
    text at the Plaintext prompt.

    Result:

          [FAIL] The message is empty, there is nothing to encrypt.

    Exit code is 1. Because Alice refuses an empty message, the previous good
    encrypted_message.json is NOT overwritten - Bob could still decrypt the
    older message. This shows a small but real safety property.


------------------------------------------------------------------------------
 PART 4 - TALKING POINTS CHEAT SHEET
------------------------------------------------------------------------------

  SYMMETRIC ENCRYPTION
    One key encrypts and decrypts. Fast. Both parties must already share it.
    The hard part in real life is getting the key to Bob safely - that is what
    asymmetric crypto (RSA, Diffie-Hellman) is for.

  AES-256
    256-bit key. Block cipher. Brute-forcing 2^256 keys is infeasible.

  GCM MODE
    Turns AES into an AEAD cipher: confidentiality PLUS integrity and
    authenticity. Decryption is all-or-nothing.

  NONCE
    Number used once. 96 bits, random, public, fresh for every encryption.
    NEVER reuse with the same key.

  TAG
    128 bits, computed from key + nonce + ciphertext. Detects a wrong key or
    ANY modification. Not a signature - it only proves knowledge of the shared
    key.

  KEY FINGERPRINT
    First 16 hex chars of SHA-256(key). Lets two people compare keys safely
    without revealing them.

  BASE64
    Just an encoding so bytes can be shown/copied as text. Adds ZERO security.

  WHEN THE TAG FAILS
    The library raises InvalidTag and NO plaintext is released. The program
    prints one clear message and exits with code 2.
